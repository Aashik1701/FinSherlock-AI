# FinSherlock AI

**Agentic AML Investigation Platform** — Société Générale Hackathon, Problem Statement 1

FinSherlock AI is an AI-powered junior AML (Anti-Money Laundering) investigator. An analyst asks a question in plain English; the system decides what analysis is needed, runs only that analysis, and returns evidence-backed findings with an escalation recommendation.

---

## What Makes This Different From a Fixed Pipeline

Most fraud-detection tools run every transaction through the same sequence of steps regardless of what was asked. FinSherlock AI separates two responsibilities:

- **Planner (Brain 1)** — a large language model that reads the analyst's query, identifies intent, extracts filters, and emits a structured JSON execution plan naming only the tools needed to answer *this specific question*.
- **Tool Layer (Brain 2)** — independent, deterministic analytical tools (EDA, feature engineering, anomaly detection, graph analysis, risk classification, explanation) that do the actual number-crunching.

The LLM never decides whether something is fraud. It only decides which tools to call and in what order. All fraud decisions are made by deterministic code, keeping the system fully explainable and auditable.

**The proof of "agentic, not pipeline" — visible in live demo:**

| Query | Tools called |
|-------|-------------|
| `"Find structuring patterns in the last 30 days"` | `run_eda` → `engineer_features` |
| `"Explain customer 1098"` | `engineer_features` only — EDA skipped entirely |

---

## AML Typologies Detected

| Typology | What it looks like | Detection signal |
|---|---|---|
| **Structuring** | Deposits/withdrawals clustered just below the $10,000 reporting threshold | Near-threshold transaction count per account over a rolling window |
| **Smurfing** | Large sum split across many small transfers to/from multiple accounts | Fan-in/fan-out degree in the transaction graph |
| **Layering** | Funds passed through a chain of intermediary accounts to obscure origin | Multi-hop paths and short holding times in the transaction graph |

## System Architecture

```
ANALYST QUERY (natural language)
        │
        ▼
┌─────────────────────┐
│   PLANNER AGENT     │  ← LLM (Groq / Gemini via litellm)
│   intent · filters  │    or deterministic keyword fallback
│   target pattern    │
└──────────┬──────────┘
           │  JSON execution plan
     ┌─────┼─────┬──────────┬──────────┐
     ▼     ▼     ▼          ▼          ▼
   EDA  Feature Anomaly   Graph     Risk
       Eng    Detection  Analysis  Classifier
     └─────┴─────┴──────────┴──────────┘
                    │
           ┌────────▼────────┐
           │  EXPLAINABILITY │  grounded NL — evidence-cited only
           │     ENGINE      │
           └────────┬────────┘
                    │
           ┌────────▼────────┐
           │   INVESTIGATION │
           │ REPORT/DASHBOARD│
           └─────────────────┘
```

## Dataset

**Primary:** IBM Transactions for Anti-Money Laundering (AML)
- Kaggle: [`ealtman2019/ibm-transactions-for-anti-money-laundering-aml`](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml)
- Purpose-built for AML detection; includes labeled laundering typologies (structuring, layering, fan-out), multiple accounts/banks/currencies
- The dataset is synthetic — generated by IBM Research to simulate realistic financial crime patterns

**Schema assumptions:**

The CSV loader auto-detects column names case-insensitively and prints a mapping on every run. Internal canonical names and the source columns it looks for:

| Internal column | Source candidates |
|---|---|
| `transaction_id` | `TRANSACTION_ID`, `id`, `Index` |
| `timestamp` | `TIMESTAMP`, `Date` |
| `sender_account_id` | `FROM_ACCOUNT`, `from_account`, `From Account` |
| `receiver_account_id` | `TO_ACCOUNT`, `to_account`, `To Account` |
| `amount` | `AMOUNT`, `Amount`, `USD_AMOUNT` |
| `currency` | `CURRENCY`, `Currency` *(optional)* |
| `transaction_type` | `TRANSACTION_TYPE`, `Type`, `Payment Type` *(optional)* |
| `country` | `FROM_COUNTRY`, `Country`, `From Bank Country` *(optional)* |
| `channel` | `CHANNEL`, `Payment Format` *(optional)* |
| `is_laundering` | `IS_LAUNDERING`, `Laundering`, `Label` *(optional)* |

If `transaction_id` is absent, synthetic IDs are generated automatically.

## Setup

**Requirements:** Python 3.11+, pip

```bash
# 1. Clone and enter the backend
cd backend

# 2. Create a virtual environment (Python 3.11 recommended)
python3.11 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 3. Install dependencies
```

## Loading the Dataset

Place the IBM AML CSV at `backend/data/raw/transactions.csv`, then:

```bash

python scripts/load_data.py --csv /path/to/your/file.csv
```

## API Endpoints

### `POST /investigate`

The main agentic endpoint. Accepts a plain-English query; runs the full planner → orchestrator pipeline.

```bash
curl -X POST http://localhost:8000/investigate \
  -H "Content-Type: application/json" \
  -d '{"query": "Find structuring patterns in the last 30 days"}'
```

**Response shape:**
```json
{
  "plan": {
    "intent": "pattern_scan",
    "filters": { "window_days": 30, ... },
    "target_pattern": "structuring",
    "plan": [
      { "tool": "run_eda",           "args": {} },
      { "tool": "engineer_features", "args": { "window_days": 30, "persist": false } }
    ],
    "planner_source": "deterministic"
  },
  "results": {
    "run_eda":           { "total_rows": 150000, ... },
    "engineer_features": { "accounts_processed": 4321, "features": [...] }
  },
  "timing":  { "run_eda": 0.42, "engineer_features": 1.17 },
  "errors":  []
}
```

`planner_source` tells you whether the plan came from an LLM (`"llm:groq/llama-3.3-70b-versatile"`) or the deterministic fallback (`"deterministic"`).

### `POST /tools/{name}`

Call any registered tool directly, bypassing the LLM — useful for debugging or demo isolation.

```bash
# Run EDA on the last 60 days
curl -X POST http://localhost:8000/tools/run_eda \
  -H "Content-Type: application/json" \
  -d '{"args": {"date_from": "2023-01-01", "date_to": "2023-03-31"}}'

# Feature engineering for one account
curl -X POST http://localhost:8000/tools/engineer_features \
  -H "Content-Type: application/json" \
  -d '{"args": {"account_ids": ["ACC_A"], "window_days": 30, "persist": false}}'
```

### `GET /tools`

List all registered tools with descriptions.

### `GET /tools/llm-schemas`

Return the OpenAI-compatible function-calling schemas for all tools — this is what gets sent to the LLM.

## LLM Configuration

The system works fully offline (no API keys) using the deterministic keyword-based planner. To enable LLM planning:

```bash
# backend/.env
GROQ_API_KEY=your_key_here       # https://console.groq.com/keys
GEMINI_API_KEY=your_key_here     # https://aistudio.google.com/app/apikey
```

Provider fallback order: Groq (primary) → Gemini → deterministic. If both fail or rate-limit, the deterministic fallback kicks in automatically — the demo never goes dark.

## Tool Registry — How to Add a New Tool

Every new analytical capability needs exactly one registration:

```python
# tools/my_new_tool.py
from pydantic import BaseModel
from agent.registry import tool

class MyToolArgs(BaseModel):
    account_id: str
    window_days: int = 30

@tool(
    name="my_new_tool",
    description="What this tool does, surfaced to the LLM and Swagger UI",
    schema=MyToolArgs,
)
def my_new_tool(args: MyToolArgs) -> dict:
    ...
```

Then add one import to `tools/__init__.py`:

```python
from tools import my_new_tool  # noqa: F401
```

That's all. The tool automatically appears in:
- `GET /tools/llm-schemas` — so the LLM can plan with it
- `POST /tools/my_new_tool` — as a standalone Swagger endpoint
- The pytest loop in `tests/conftest.py`

## AI and Tool Disclosure

This project uses the following AI/ML components:

| Component | Technology | Role |
|---|---|---|
| **Planner agent** | Llama 3.3 70B via Groq API (free tier), fallback: Gemini 2.0 Flash via Google AI Studio (free tier), accessed through `litellm` | Parses analyst queries into structured execution plans. Does NOT make fraud decisions. |
| **Anomaly detection** (planned) | Scikit-learn `IsolationForest` + hand-written rule functions | Detects statistically unusual transaction patterns |
| **Graph analysis** (planned) | `networkx` | Detects smurfing (fan-in/fan-out) and layering (multi-hop chains) |

All fraud-detection decisions are made by deterministic code, not the LLM. The LLM's only role is to parse the intent of a query and select which analytical tools to invoke.
